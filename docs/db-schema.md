# Схема базы трендвотчера — PostgreSQL / Supabase

Черновик для проверки глазами. SQL (`db/001_init.sql`) пишется после согласования.
Опирается на паспорт продукта (`passport_and_sources.xlsx`, лист «Паспорт трендвочера»),
карту источников (лист «Карта источников», `sources.yaml`) и `SPEC.md`.

Три таблицы:

- **sources** — откуда забираем: адреса, способ загрузки, состояние;
- **events** — что увидели: одна строка на один материал (одну ссылку);
- **digests** — что отправили в Telegram: одна строка на одну недельную сводку.

Связи: событие ссылается на свой источник и на сводку, в которую попало.

```
sources 1 ──── N events N ──── 1 digests
```

---

## sources — источники

Одна строка — один адрес, который сборщик опрашивает. Новый адрес = новая строка,
программу не трогаем.

| Поле | Тип | Обязательно | Что это |
|---|---|---|---|
| `id` | текст, **первичный ключ** | да | короткое имя источника, как в `sources.yaml`: `kts_site`, `agima_blog_habr`. Не меняется — на него ссылаются события |
| `company` | текст | да | компания, как в паспорте: `KTS`, `Napoleon IT`, `red_mad_robot`… |
| `kind` | текст из списка | да | что за источник: `vacancies`, `articles`, `cases`, `site` |
| `method` | текст из списка | да | как забираем: `hh_api`, `rss`, `sitemap`, `sitemap_index` |
| `url` | текст, **уникальный** | да | адрес ленты, карты сайта или запроса к API. Один адрес не может быть заведён дважды |
| `settings` | JSON | да, по умолчанию пусто `{}` | настройки, которые зависят от способа загрузки: `employer_id` для hh, правила `classify` и `default_signal` для карт сайта, `track_lastmod_for` и т. п. |
| `note` | текст | нет | комментарий человеку: почему выключен, что проверить |
| `enabled` | да/нет | да, по умолчанию «да» | **включён ли.** Выключенный источник сборщик пропускает. Так ставим на паузу hh-источники, пока нет токена |
| `last_checked_at` | дата и время | нет | **когда последний раз обращались**, с любым исходом. Пусто — ни разу |
| `last_success_at` | дата и время | нет | **когда последний раз успешно ответил.** Пусто — ни разу |
| `consecutive_errors` | целое ≥ 0 | да, по умолчанию 0 | **сколько ошибок подряд.** Успешный ответ сбрасывает в 0. По нему строится блок «Источники» в сводке |
| `last_error` | текст | нет | короткий текст последней ошибки: `403 forbidden`, `timeout 30s`. Обнуляется при успехе |
| `baseline_done_at` | дата и время | нет | когда прошёл первый, «немой» прогон (SPEC, раздел 2, правило 1). Пусто — следующий прогон только запоминает ссылки и событий не рождает. При правке `settings.classify` сбрасываем в пусто |
| `created_at` | дата и время | да, ставит база | когда строку завели |

Что сознательно **не** в этой таблице:

- дыры покрытия (`status: none` в реестре: вакансии R77 AI, Telegram-каналы) — опрашивать нечего, они остаются в `sources.yaml: coverage_gaps`;
- `user_agent` и токен hh — это настройки сборщика, а не источника; они остаются в `.env`/конфиге. К тому же в `user_agent` сейчас стоит личный email — в базу он не попадает.

## events — события

Одна строка — один материал (вакансия, статья, кейс, страница), который сборщик
хоть раз увидел, **включая шум**. Таблица заодно служит списком уже виденных ссылок:
по ней сборщик понимает, что новое, а что нет.

| Поле | Тип | Обязательно | Что это |
|---|---|---|---|
| `url` | текст, **первичный ключ** | да | канонический адрес материала (без `utm_*`, `hhtmFrom`, `https`, без `/` в конце — SPEC, раздел 1). **Это и есть ключ события.** Повторный прогон с той же ссылкой не создаст вторую строку — база откажет, сборщик просто пропустит |
| `source_id` | текст → `sources.id` | да | откуда пришло. Компания берётся из источника, отдельно не хранится |
| `signal` | текст из списка | да | тип: `vacancy_ai`, `vacancy_other`, `article`, `case`, `new_page`, `page_changed` |
| `verdict` | текст из списка | да | итог правил: `event` — в сводку, `keep` — в сводку в блок «Остальное», `noise` — не показывать |
| `reason` | текст | нет | какое правило сработало, словами — для разбора спорных случаев |
| `title` | текст | да | заголовок из ленты или название вакансии; у ссылок из карты сайта — последний сегмент пути |
| `published_at` | дата и время | **нет** | **когда материал опубликован.** Пусто, если источник даты не даёт (карты сайта Napoleon IT, KTS) |
| `discovered_at` | дата и время | **да** | **когда сборщик увидел впервые.** Ставит сборщик сам, у базы значения по умолчанию нет — забытая дата станет ошибкой, а не тихим «сейчас». По нему сортируем, если `published_at` пусто |
| `is_baseline` | да/нет | да, по умолчанию «нет» | увидено во время «немого» прогона источника — запомнено, но в сводку не идёт |
| `duplicate_of` | текст → `events.url` | нет | если это та же статья, что уже пришла из другого источника (сайт + Хабр, `dedup_groups`), — ссылка на основную запись. В сводке показывается только основная, вторая ссылка — рядом с ней |
| `city` | текст | нет | город из вакансии |
| `experience` | текст | нет | требуемый опыт из вакансии: «1–3 года» |
| `industry` | текст | нет | отрасль клиента из кейса, если источник её даёт |
| `co_companies` | список текстов | нет | компании-соавторы публикации на Хабре: `{Альфа-Банк}`. Только названия компаний |
| `lastmod` | дата и время | нет | дата изменения страницы из карты сайта — для `page_changed` у источников с `track_lastmod_for` |
| `digest_id` | число → `digests.id` | нет | в какую сводку попало. Пусто — ещё не отправлялось. Так одно событие не попадёт в две сводки |
| `useful` | да/нет | нет | отметка для метрики паспорта: «переслал команде / обсудил». Пусто — не отмечено |

Чего здесь нет из `SPEC.md`:

- `id = sha1(company + url)` — не нужен, ключом стала сама ссылка;
- `payload.raw` (сырой ответ источника) — **убран намеренно.** В ответе hh у вакансии бывает блок `contacts` с именем и телефоном рекрутера, в ленте Хабра — ник автора. Храним только поля, перечисленные выше, — персональным данным некуда попасть.

## digests — сводки

Одна строка — одна недельная сводка.

| Поле | Тип | Обязательно | Что это |
|---|---|---|---|
| `id` | число, **первичный ключ**, ставит база | да | номер сводки |
| `period_start` | дата, **уникальная** | да | первый день недели, за которую сводка. Вторую сводку за ту же неделю база не примет — ручной перезапуск не продублирует отправку |
| `period_end` | дата | да | последний день недели; не раньше `period_start` |
| `body` | текст | да | текст сообщения ровно в том виде, в каком ушло в Telegram, в том числе «изменений нет» |
| `created_at` | дата и время | да, ставит база | когда собрали |
| `sent_at` | дата и время | нет | когда Telegram подтвердил отправку. Пусто — собрали, но не отправили (ошибка доставки) |
| `telegram_message_id` | число | нет | номер сообщения, который вернул Telegram, — доказательство доставки |

Чего здесь нет: `chat_id` получателя. Это идентификатор конкретного человека
в Telegram — он остаётся в `.env`, как и токен бота.

## Персональные данные

В схеме нет полей для имён, ников, телефонов, email, ссылок на профили людей.
Сырые ответы источников не сохраняются. Свободный текст есть только в `note`,
`reason`, `last_error`, `title` и `body` — туда пишет сборщик или вы сами,
а не источник целиком.

## Доступ в Supabase

Таблицы лягут в схему `public`, а её Supabase по умолчанию отдаёт наружу через API.
Поэтому на всех трёх включаем Row Level Security **без политик**: анонимный ключ
не прочитает ничего, сборщик ходит с `service_role`-ключом из `.env`, который RLS обходит.

## Принятые решения

Согласовано 16.10.2026, схема создаётся файлом `db/001_init.sql`.

1. **Обновление страницы (`page_changed`) при ключе «одна ссылка — одна строка».**
   Изменившаяся страница — та же ссылка, вторую строку база не даст. Поэтому
   существующая строка обновляется: новый `lastmod`, `signal = page_changed`,
   `digest_id` обнуляется, и строка снова попадает в ближайшую сводку. Что она
   уже была в прошлой сводке, при этом забывается. Касается только двух
   источников с `track_lastmod_for`.
2. **Правила классификации лежат в `sources.settings`**, чтобы новый адрес
   заводился целиком без правки кода. Источник правды по списку источников —
   база, `sources.yaml` — начальное наполнение.
3. **Одна статья у двух конкурентов.** Если совместная статья на Хабре придёт
   из лент двух компаний, строка будет одна — за тем источником, который увидел её
   первым; вторая компания остаётся в `co_companies`.
