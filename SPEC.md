# Трендвотчер конкурентов — структура данных

Версия от 16.10.2026 — под базу в Supabase.
Опирается на паспорт продукта (`passport_trendwatcher.docx`), схему базы
(`docs/db-schema.md`, `db/001_init.sql`) и реестр источников (`sources.yaml`).
Источник правды по адресам и правилам классификации — таблица `sources` в базе;
`sources.yaml` — её начальное наполнение и описание замеров. Этот файл — о том,
что с источниками делать.

**Правило проекта: только белые источники.** Официальные API, RSS и карты сайтов.
Никакого обхода авторизации и капчи, никакого разбора вёрстки страниц —
ни для списков статей, ни для дат, ни для текста. Если по компании белого
источника нет, это фиксируется как дыра (`sources.yaml: coverage_gaps`),
а не закрывается парсингом HTML.

---

## 1. Модель события

Событие — один материал (вакансия, статья, кейс, страница) у одного конкурента.
Хранится строкой таблицы `events`; полное описание полей — `docs/db-schema.md`.

```yaml
event:                 # строка events
  url:           # канонический адрес — он же ключ: одна ссылка — одна строка, навсегда
  source_id:     # id источника (sources.id); компания берётся из источника
  signal:        # vacancy_ai | vacancy_other | article | case | new_page
  title:         # из ленты; у URL из карты сайта заголовка нет — берём последний сегмент пути
  published_at:  # дата публикации; null, если источник её не даёт
  discovered_at: # когда сборщик увидел впервые — им и сортируем, если published_at нет
  verdict:       # event | noise | keep — результат правил из раздела 4
  reason:        # какое правило сработало, текстом: для разбора спорных случаев
  is_baseline:   # увидено в немом прогоне источника — в сводку не идёт (раздел 2)
  duplicate_of:  # url основной записи, если та же статья пришла из другого источника
  city, experience:  # из вакансии
  industry:      # отрасль клиента, если источник её даёт (<category> в кейсах R77)
  co_companies:  # компании-соавторы из dc:creator Хабра: «Welltraum (Selectel, red_mad_robot)»
```

Сырой ответ источника не хранится: в нём бывают персональные данные (контакты
рекрутера у hh, ники авторов у Хабра). Пишем только перечисленные поля.

Обновления страниц не отслеживаются: сигнала `page_changed` нет (решение 16.10.2026,
`docs/db-schema.md`, «Принятые решения», пункт 1).

### Заголовок у URL из карты сайта

Карта сайта отдаёт только адрес. Заголовок со страницы не забираем — это разбор вёрстки.
Вместо него — последний сегмент пути, с дефисами, заменёнными на пробелы:
`/success-stories/ii-recruter-industry` → «ii recruter industry». Транслит читается
плохо, но ссылка в сводке ведёт на страницу, и этого достаточно.

### Канонизация URL

Ссылка — ключ события, поэтому канонизация обязательна: иначе один и тот же
материал даст две строки. Так делает `normalize_url` в `collector.py`:

- убрать метки кампаний и переходов: `utm_*`, `hhtmFrom`, `from`, `yclid`, `gclid`,
  `fbclid`; остальные query-параметры оставить — они могут нести смысл;
- убрать якорь `#…`;
- привести к нижнему регистру хост; путь оставить как есть, только пробелы
  и кириллицу закодировать (`%20`, `%D0%BF…`);
- убрать завершающий `/`;
- `http` → `https`.

Относительная ссылка из ленты достраивается от адреса самой ленты. Ссылка, которую
база не примет (не http/https, без хоста), пропускается со счётчиком в выводе
сборщика — иначе база отклонила бы всю пачку записей источника.

### Дедупликация

Одна статья выходит и на своём сайте, и на Хабре. Группы заданы в `sources.yaml:dedup_groups`
(KTS, AGIMA). Внутри группы сравниваем нормализованный заголовок
(нижний регистр, схлопнутые пробелы, снятая пунктуация). При совпадении —
основной считается запись из источника с датой публикации, у второй
`duplicate_of` указывает на основную. В сводке — одна строка, вторая ссылка рядом.

Совместная статья на Хабре в лентах двух компаний приходит с одной и той же ссылкой
(проверено 16.10.2026 на статьях KTS с Альфа-Банком), поэтому дубля не даёт вовсе:
строка одна, за тем источником, который увидел её первым.

У статей из карты сайта заголовка нет, поэтому сравнение идёт по slug против
транслитерированного заголовка с Хабра — совпадение будет неполным. Что на практике
пересекается, а что нет — проверка в `BACKLOG.md`.

### Соавторы на Хабре — сигнал о клиенте

В ленте Хабра автор подписан компаниями: `sskussev (KTS)`. Если в скобках кроме
самой компании есть другая — `(Альфа-Банк, KTS)`, — это совместная публикация,
и вторая компания почти всегда клиент или партнёр. Такие компании пишем в
`events.co_companies` — только названия компаний, без ников авторов.

По паспорту партнёрство — шум, а клиент — событие. Автоматически их не различить,
поэтому совместная статья идёт в сводку с пометкой «совместно с X», а решение
остаётся за читателем. Отдельно ценно совпадение: один и тот же клиент у двух
конкурентов. На 15.10.2026 так выглядит Альфа-Банк: соавтор двух статей KTS и клиент
в кейсе R77 AI.

## 2. Что хранить между запусками

Всё состояние — в базе Supabase, локальных файлов нет. Минимум, при котором
«новое» определяется честно:

| Что | Где | Зачем |
|---|---|---|
| уже виденные ссылки | `events.url` | основной способ отличить новое от старого: повторную ссылку база не примет, сборщик её просто пропустит |
| повторная публикация вакансии | `events.url` | у вакансии hh своя ссылка с её id — та же вакансия даёт ту же ссылку |
| немой прогон пройден | `sources.baseline_done_at` | первый прогон источника событий не рождает (правило 1) |
| когда обращались, когда успешно | `sources.last_checked_at`, `sources.last_success_at` | для блока «Источники» и разбора сбоев |
| ошибки подряд | `sources.consecutive_errors`, `sources.last_error` | для блока «Источники» в сводке |
| что уже отправлено | `digests`, `events.digest_id` | сводка за неделю одна (`period_start` уникален), событие не попадёт в две сводки |

Граница окна сводки — события с `digest_id` пусто, не `is_baseline` и не `noise`
(индекс `events_pending_idx`).

Три правила, без которых состояние врёт:

1. **Первый прогон источника не рождает событий.** Он только запоминает ссылки:
   строки пишутся с `is_baseline = true` и в сводку не идут.
   Правило действует **для каждого источника отдельно**, а не для всего парсера:
   поле `baseline_done_at`. Это важно для карт сайтов — они забираются
   целиком, и без немого прогона AGIMA выдаст 137 «новых кейсов», а Napoleon IT —
   27. То же при любой правке `settings.classify`: у изменённого источника
   `baseline_done_at` сбрасывается в пусто, и он заново проходит немой прогон.
2. **Источник, вернувший ошибку, не трогает события.** Иначе пустой ответ
   из-за таймаута превратит все его URL в «исчезнувшие», а на следующей неделе —
   в «новые». Меняются только поля ошибки в `sources`. Сбой одного источника —
   в том числе сбой записи его состояния — не прерывает прогон остальных.
3. **Тишина — не ошибка.** Тревога в сводке поднимается только по ошибкам загрузки,
   а не по отсутствию новых записей. Источники с `dormant: true` и компании из
   `coverage_gaps` молчат ожидаемо — иначе тревога по red_mad_robot и R77 AI
   горела бы каждую неделю и приучила бы её не читать.

## 3. Классификация сигнала

Карты сайтов забираются **целиком**, а не только раздел блога, и раскладываются
по сигналам после загрузки. Так ловятся кейсы и новые страницы услуг — без единого
нового источника: данные и раньше скачивались, но отрезались фильтром `/blog/`.

Порядок применения:

1. Общий шум по пути из `defaults.noise_paths` — отбрасывается сразу.
2. Правила источника: `classify` (по пути, первое совпадение побеждает)
   или `classify_by_child` (по дочерней карте, из которой пришёл URL).
3. Всё, что не совпало, получает `default_signal` — у сайтов это `new_page`.

| Компания | Статья | Кейс | Новая страница | Шум |
|---|---|---|---|---|
| KTS | `/posts/` | `/cases/` | остальное: proptech, hrtech, finops, devops, wolfram-wfm, solutions | `/awards/`, `/articles` |
| Napoleon IT | `/blog/` | `/cases/`, `/stories/` | остальное: solutions, industries, services | press-center, reviews, career, internship, about-us, contacts |
| Just AI | `blog-sitemap` | `case-sitemap` | `page-sitemap`, `solutions-sitemap` | `category-sitemap`; страницы мероприятий по slug |
| AGIMA | `/blog/` | `/projects/` | остальное: approach, special-projects | `/events/`, `/careers/`, about, clients, contacts |
| R77 AI | — | `/cases/tpost/` | — | — |
| Хабр, все компании | `/ru/companies/<слаг>/articles/` | — | — | — |
| Siberian.pro, Nord Clan | `/blog/` из RSS | — | — | — |

Полные правила — в `sources.yaml`, таблица выше их пересказывает. В базе они
переезжают в `sources.settings` вместе с карточкой источника.

**Общий шум по пути** соответствует строкам паспорта «глоссарии, страницы авторов,
теги и прочие SEO-страницы» и «технические страницы: политики, согласия, юр. информация»:

```
/glossary/      /authors/       /tags/        /tag/
/policy         /privacy        /terms        /cookie
/personal-data  /soglasie       /legal        /sitemap
```

### Изменение страниц не отслеживается

Паспорт называет событием «изменение цен, тарифов или формулировок». Без разбора
страницы единственный белый признак — изменился `lastmod` у уже известного URL,
и то лишь у Just AI и AGIMA (у Napoleon IT `lastmod` нет совсем, у KTS — только
у кейсов). Причём `lastmod` говорит, что страница изменилась, но не что именно:
правка цены и замена баннера выглядят одинаково.

Поэтому 16.10.2026 решено обновления страниц не отслеживать: `lastmod` не храним,
сигнала `page_changed` нет. Одна ссылка — одна строка, навсегда. Изменение цен
и формулировок — признанная дыра (`sources.yaml: coverage_gaps`).

## 4. Правила: событие, шум, остаётся в сводке

Прямо из паспорта, в порядке применения.

### Отсекаем как шум

| Правило | Как проверяем |
|---|---|
| Вакансии не из ИИ-направлений | в названии нет ни одного ИИ-признака (ниже) и есть признак другой роли: продажи, HR, бухгалтерия, рекрутмент, поддержка |
| Повторная публикация той же вакансии | ссылка с тем же id вакансии уже есть в `events`, либо совпадает нормализованное название у того же работодателя за последние 90 дней |
| Технические страницы, глоссарии, авторы, теги, SEO | общий шум по пути (раздел 3) |
| **Дайджесты общих новостей под именем компании** | правила `exclude_title_patterns` и `exclude_url_patterns` источника. Сейчас — Siberian.pro: еженедельные «Главные новости AI: дайджест» — 4 из 10 последних записей ленты |
| **Страницы мероприятий** | `exclude_slug_patterns` источника. Сейчас — Just AI: хакатоны, бизнес-ужины, конференции лежат в той же карте, что и продуктовые страницы |
| Не события: всплеск найма, закрытие вакансий, партнёрства, премии, рейтинги, конференции | закрытие — исчезновение из ленты, не публикуем. Остальное — по заголовку (список ниже) |

**Признаки рейтингов, премий и конференций в заголовке** (эвристика, настроить на первых прогонах):

```
рейтинг, вошла в топ, вошёл в топ, премия, награда, лауреат,
конференци, форум, хакатон, что обсудили, итоги года
```

Пример из замера: в блоге Just AI из четырёх свежих статей две — «вошла в топ-4 платформ
по версии…» и «что обсудили на летней конференции». Обе по паспорту шум.

Обзоры рынка вроде «ТОП-8 российских RAG-систем» у Nord Clan под это правило
**не попадают** намеренно: это статья про ИИ, а не рейтинг самой компании.
Их громкость гасится лимитом в сводке (раздел 5), а не фильтром.

### Считается событием

| Сигнал | Условие |
|---|---|
| `vacancy_ai` | в названии вакансии есть ИИ-признак |
| новое направление | вакансия с признаком, которого у этой компании раньше не встречалось — сверяем по прежним вакансиям компании в `events` |
| `new_page` | новый URL с классом `new_page` (раздел 3) |
| `case` | новый URL с классом `case` |
| `article` | новый URL с классом `article`, свой сайт или Хабр |

**ИИ-признаки в названии вакансии** (регистронезависимо, по словам):

```
ML, machine learning, машинное обучение, LLM, NLP, CV, computer vision,
MLOps, prompt, промпт, data scientist, AI, ИИ, нейросет, GenAI, RAG
```

Список намеренно широкий: пропущенная ИИ-вакансия дороже лишней строки в сводке.

**Softline digital.** Вакансии приходят по работодателю всей группы (hh 2381). ИИ-признак
отбирает из них профильные, но не отвечает на вопрос, digital это или другое
подразделение. В сводке такие вакансии подписываются «Softline (группа)».

### Остаётся в сводке

Паспорт отдельно оговаривает, что это **не** шум и из сводки не выбрасывается,
а идёт отдельным блоком: стажировки и junior-вакансии, статьи не про ИИ,
публикации на сторонних площадках (Хабр, vc.ru, Telegram). Сюда же — совместные
публикации с пометкой «совместно с X». В базе это `verdict = 'keep'`.

## 5. Формат сводки

Получатель один, канал Telegram, раз в неделю, понедельник 9:00 по Москве.

Структура сообщения:

```
Трендвотчер · 20–26 октября

ГЛАВНОЕ
  • <компания> — <что случилось, одной строкой>
  ...

<Компания>
  [вакансия ИИ]  Senior NLP Engineer · 22.10 · <ссылка>
  [кейс]         Телеком-оператор · 24.10 · <ссылка>
  [новая страница] agent platform enterprise · 24.10 · <ссылка>

<Компания>
  [статья] Как мы считали RAG · 21.10 · Хабр · <ссылка>
  …и ещё 4 статьи

ОСТАЛЬНОЕ
  стажировки, статьи не про ИИ, совместные публикации —
  списком, без подробностей

ИСТОЧНИКИ
  ошибка загрузки третью неделю подряд: <source_id>
```

Правила подачи:

- **Блок «Главное» — не больше трёх строк.** Сводку читают в телефоне утром
  в понедельник; если главного нет, блок не печатается вовсе.
- **Приоритет сигналов**: вакансия ИИ и новое направление → кейс → новая страница →
  статья. Статья — самый слабый сигнал и в «Главное» попадает, только если больше ничего нет.
- **Не больше трёх статей от одной компании**, остальные сворачиваются в «…и ещё N статей».
  Без лимита сводку займут самые громкие блоги: Nord Clan даёт почти две статьи в неделю,
  а сигнальные AGIMA, SimbirSoft и KTS вместе — около полутора. Сводка должна показывать,
  кто меняет направления, а не кто чаще пишет.
- Группировка по компаниям, внутри — по дате.
- У каждого события тип в квадратных скобках, дата, прямая ссылка.
- Сторонняя площадка называется явно («Хабр»), иначе непонятно, почему ссылка уводит с сайта.
- Блок «Источники» появляется только при ошибках загрузки. Тишина источника тревогой
  не считается (раздел 2, правило 3).

Неделя без событий — открытый вопрос паспорта: присылать короткое «изменений нет»
или не присылать ничего. До решения парсер шлёт «изменений нет» — молчание
неотличимо от поломки.
